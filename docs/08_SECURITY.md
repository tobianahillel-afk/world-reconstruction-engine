# Security and supply-chain baseline

WRE uses a deliberately small security baseline that improves confidence without turning routine development into a slow approval process.

## Reproducible development environment

- Python development dependencies are declared in `pyproject.toml`.
- `uv` is pinned to `0.12.13` in the project and GitHub Actions bootstrap.
- `uv.lock` is committed and generated by the pinned toolchain.
- Fast CI installs with `uv sync --frozen --group dev`; a stale or incompatible lockfile therefore fails instead of being silently regenerated.
- GitHub Actions used by WRE are pinned to full commit SHAs. Version comments remain next to the SHA for readability.

## Dependency updates

Dependabot is configured for two ecosystems:

- native `uv` dependency updates;
- GitHub Actions updates.

Both run weekly and group related updates to reduce PR noise. Dependency-update PRs are never assumed safe merely because Dependabot created them: they still go through normal CI and review.

## Pull-request dependency review

Dependency Review runs separately from `fast-ci` when dependency manifests, lockfiles or GitHub Actions change. It checks runtime, development and unknown scopes and fails on newly introduced vulnerabilities of **moderate severity or higher**.

GitHub's Dependency Review action requires the repository **Dependency Graph**. The current connector cannot safely enable that repository setting. The workflow therefore performs a preflight against GitHub's dependency-graph SBOM endpoint:

- HTTP `200`: the graph is available and strict Dependency Review runs normally;
- HTTP `403` or `404`: the workflow records an explicit warning and skips only the unavailable review step;
- any other API response is treated as an error and fails the job.

This is a capability check, not a security bypass. Once Dependency Graph is enabled in GitHub repository settings, strict Dependency Review becomes active automatically without another repository change. Until then, do not claim Dependency Review itself is active.

Keeping this separate means normal source-only PRs do not pay the dependency-review cost.

## Code scanning

CodeQL runs in a separate workflow for Python changes, on relevant pull requests and pushes to `main`, plus a weekly scheduled scan. It is intentionally not part of the latency-sensitive `fast-ci` job.

## Secrets

Secrets, credentials, tokens and private keys must never be committed to source, fixtures, example configs or benchmark datasets.

This repository is public, so GitHub security capabilities such as secret scanning and push protection may be available. Their exact account/repository toggle state is **not inferred from repository visibility** and cannot be reliably changed through the current GitHub connector. Verify these settings in GitHub repository settings before treating them as active controls.

## Main-branch rules

Recommended repository rules for `main` are:

- changes through pull requests;
- required `fast` status check;
- no force pushes;
- no branch deletion;
- resolved review conversations before merge where practical.

The current connector does not expose a safe ruleset/branch-protection write action for these settings. Until verified manually in GitHub settings, treat them as recommendations rather than configured guarantees.

## Dependency licensing

L0.4 does not choose WRE's final project license and does not promote any native reconstruction candidate to a mandatory dependency. Every future mandatory dependency still requires the license review recorded in `registry/dependencies.yaml`.

A top-level repository license is not sufficient evidence for every artifact shipped or consumed by a dependency. Integration review must separately consider, when applicable:

- library/source-code license;
- bundled native components or vendored files with distinct notices;
- model/checkpoint/weight licenses;
- test/example datasets and their redistribution terms;
- subprocess/container distribution implications;
- attribution/NOTICE requirements.

Candidate status means "worth evaluating", not "cleared for redistribution". Any selected model, checkpoint, test dataset or bundled subcomponent must be reviewed before becoming part of a required WRE distribution.

## Response to findings

- Do not weaken a security gate merely to make a PR green.
- Investigate whether the finding is reachable/relevant and whether an upstream patched version exists.
- If an exception is genuinely required, record the rationale explicitly rather than silently suppressing it.
- Security automation should remain proportional: expensive checks stay outside `fast-ci` unless evidence shows they belong on every PR.
